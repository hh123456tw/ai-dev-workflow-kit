# CodeGraph（colbymchenry）在自有 repo 任務上的 A/B：加了 MCP 之後有沒有變快、變省

**日期：** 2026-10-23
**Harness：** `own-repo-plugins-g2`（沿用，只新增 arm）
**證據位置：** `~/opencode-benchmarks/own-repo-tasks/`（不放在這個 repo 裡）。`manifest-cg.json` 是鎖定的順序，`run-cg.py` 是執行器，`analyze-cg.py` 是配對分析，`runs/` 和 `runs.jsonl` 是原始紀錄。
**要回答的問題：** `colbymchenry/codegraph`（約 7.5 萬顆星）在使用者自己的 repo 上，能不能在不降低品質的前提下，讓 Claude Code 改程式更快或更省？
**結論：不建議安裝。** 在這 20 組配對上，品質、時間、成本都沒有可偵測的差異。模型只在 20 格裡的 6 格用了它。

## 方法

- **受測物：** `@colbymchenry/codegraph` 1.6.2（MIT，npm 最後更新 2026-10-03），Windows x64 原生版本。它只暴露一個 MCP 工具：`codegraph_explore`。
- **隔離安裝：** 用 `npm install --prefix` 裝在 `~/opencode-benchmarks/tools/codegraph`。沒有執行 `codegraph install`，所以沒有改動 `~/.claude.json`、`~/.claude/CLAUDE.md` 或權限設定。套件 metadata 沒有列出 postinstall 腳本。
- **隱私：** 它預設開啟匿名使用統計。測試前執行了 `codegraph telemetry off`，緩衝中未送出的資料也被刪除；MCP 設定另外帶 `CODEGRAPH_TELEMETRY=0`。
- **兩個 arm（其餘設定完全相同）：**
  - `cc-base`：Sonnet 5.5、Ponytail 5.3.1（`--plugin-dir`，commit `84740e3`）、當時的全域 CLAUDE.md 規則（含快速測試規則、STE 寫法、編碼規則，沒有變異測試那條）、沒有 MCP。
  - `cc-cg`：同上，再加 `--mcp-config`（`codegraph serve --mcp`，`alwaysLoad: true`）和 `mcp__codegraph__*` 的 allowedTools。
- **索引：** `cc-cg` 的每個 worktree 在計時前先跑 `codegraph init --yes`。索引時間另外記錄，不算進模型時間（最小 1.53 秒、中位數 5.34 秒、最大 10.11 秒）。
- **題目：** 與先前相同的 10 題：agentforge 4 題（af-2ee1366、af-4a22606、af-73052cf、af-7b2ec5a）、qingpu-insight 6 題（qp-097d734、qp-1cd6156、qp-931cc75、qp-bd7a82c、qp-d788d8f、qp-f72a686）。每題起點是 commit 的 parent，hidden test 是該 commit 改動的測試。
- **設計：** 10 題 × 2 arm × 2 次 = 40 格，依序跑。每題兩個 arm 的先後順序用固定種子（20261023）隨機決定，第二次與第一次對調。順序在第一格之前鎖定（`manifest-cg.json`，sha256 前 16 碼 `98b30412df0f8f13`）。
- **指標：**
  - 品質：hidden test 是否全綠且 HEAD 沒動（strict），要求不能比對照組差。
  - 效率：API 等值成本（`api_equivalent_usd`）、模型實際時間（`model_wall_time_s`）、工具呼叫次數。
  - 有沒有真的用到：`codegraph_calls`。可用性不等於曝光。
- **統計：** 以（題目, 次數）為單位配對，取 treatment ÷ control 的比值，對 log 比值做 10,000 次 bootstrap，報告中位數和 95% 信賴區間。
- **清理：** 每格結束後結束殘留行程（`cc-cg` 的 20 格每格結束 2 個，共 40 個；推測是 MCP 伺服器和它的 cmd 包裝，沒有逐一確認）。其中沒有 harness 逾時，也沒有索引失敗。

## 結果

### 全部 20 組（intent-to-treat）

| 指標 | treatment ÷ control（中位數） | 95% CI | treatment 較好的組數 |
| --- | ---: | ---: | ---: |
| 模型時間 | 0.94 | 0.79–1.02 | 11/20 |
| API 等值成本 | 1.10 | 0.92–1.11 | 6/20 |
| 工具呼叫次數 | 1.11 | 0.78–1.23 | 8/20 |

- strict 通過：control 14/20、treatment 15/20。唯一只有 treatment 通過的是 af-4a22606 第二輪，這題先前重跑時兩個 arm 都只過 1/4，本來就不穩。沒有任何一組是 control 過而 treatment 沒過。
- 總成本 $7.45（control）對 $8.17（treatment）；總模型時間 6,698 秒對 6,389 秒。
- 三個比值的信賴區間都包含 1：沒有證據顯示它省時間、省錢或降低品質。成本的方向偏貴。

### 曝光

- `cc-cg` 的 20 格裡只有 6 格呼叫過 `codegraph_explore`，每格剛好 1 次，總共 6 次。其餘 14 格完全沒用，行為與 control 相同。
- 讀檔與搜尋（Read、Grep、Glob）的次數中位數：control 2.0、treatment 3.0。這些任務的描述通常已經指出檔案位置，本來就不需要大量探索。
- 開跑前的單題 smoke test 也一樣：工具已連上、模型看得到它，但被問到「`create_chrome` 在哪裡被呼叫」時，模型選了 Grep 和 Bash。

### 事後分組（只能當線索，不能當證據）

| 子集 | 組數 | 模型時間 | 成本 | 工具呼叫 |
| --- | ---: | --- | --- | --- |
| 有呼叫（曝光） | 6 | 1.11（1.03–1.16），1/6 較快 | 1.28（1.16–1.32），0/6 較便宜 | 1.61（1.10–1.90） |
| 沒呼叫 | 14 | 0.90（0.70–0.98），10/14 較快 | 1.02（0.83–1.03） | 0.90（0.63–1.08） |

- 這是依結果事後分組，有選擇偏差：模型比較可能在特定任務上才去呼叫工具。
- 有呼叫的 6 組，成本全部比 control 高。這個方向值得注意，但樣本太小。
- 沒呼叫的 14 組與 control 的設定只差一個沒被用的工具，看起來較快（0.90）。這裡不解讀成 CodeGraph 的效果，較可能是任務組成和雜訊。

## 與官方數字的關係

- 官方 README 的 benchmark：7 個開源專案、7 種語言，Claude Code headless，每題中位數 4 次，比較有無 CodeGraph。平均少 88% 工具呼叫、快 53%、少 62% token、便宜 44%。VS Code（約 1.1 萬檔）快 2.2 倍，Gin（約 110 檔）快 39% 且成本「差不多」。
- 官方 harness 兩個 arm 都封鎖 `codegraph` CLI，所以對照組是乾淨的。這部分設計是對的。
- 但官方題目是「回答一個架構問題」：唯讀、探索為主，沒有改程式，也沒有 hidden test 判斷對錯。本測試的任務是改程式，探索只佔一部分，任務描述又常常點出檔案位置。兩者量的不是同一件事。
- 官方也承認一個代價：長 session 結束時，context 裡留下的檢索內容多約 80%。本測試每格都是單次任務，沒有量到這一點。
- 使用者的 repo 大小（git 追蹤的原始碼檔案數）：qingpu-insight 229、fundagent 94、agentforge 91、on_chain 38。最大的專案比官方有明顯效果的專案小一個數量級，落在官方數字「差不多」的那一端。這次結果與官方數字並不矛盾。

## 結論與限制

- **結論：** 在 100–300 個檔案的 repo 上改程式，CodeGraph 沒有可偵測的好處，品質沒有變差，成本方向偏貴。不建議安裝。
- **限制：**
  - 20 組配對，每格模型時間有 3 倍以上的自然波動。只能偵測約 20% 以上的差異，偵測不到 5% 以內的小差異。
  - 只有 6 格有曝光，曝光子集的分析是事後分組。
  - 沒有測大型專案（上千個檔案以上）、純探索問答，或長時間 session。
  - 沒有套用安裝器會寫進 `CLAUDE.md` 的那一小段說明（用來讓 subagent 知道 `codegraph explore` 指令），也沒有套用自動允許權限。這段說明可能提高 subagent 的使用率，影響沒有測。
  - 模型是 Sonnet 5.5，不是使用者日常的 Opus；換模型後是否更常呼叫工具，沒有測。
  - 兩個 arm 都開著 Ponytail。Ponytail 的「最小改動」偏好可能降低模型去探索的動機，這會讓 CodeGraph 更難被用到。這個交互作用沒有拆開測。
- **何時重測：** 要處理上千檔案的專案時，用那個專案自己的 git 歷史挖題，方法同這份文件。

## 安裝與使用上的觀察

- `codegraph init` 在 238 個檔案、7,573 個節點、19,788 條邊的專案上花 2.1 秒（含啟動共約 9 秒），產生約 24 MB 的 `.codegraph/codegraph.db`。
- `.codegraph/` 不會被自己的 `.gitignore` 忽略，在 `git status` 裡顯示為未追蹤。要用在真的 repo 上，需要自己把它加進 `.gitignore`。
- 它使用 `~/.codegraph/` 儲存全域狀態。先前測試的 `codegraph-ai/CodeGraph`（見 `2026-09-20-codegraph-core-canary.md`）也用同一個資料夾名稱，兩個專案會共用目錄。
- 官方安裝器預設會問要不要開匿名統計。本測試中關閉。
- 結束行程：MCP 伺服器在 Claude 結束後會留下背景行程，harness 需要主動結束它們。
